SkillLearnBench 调研：
AnalystBench 可借鉴之处

对比 SkillLearnBench（COLM 2026，CMU）与 AnalystBench（自研，MVP）的全量源码与文档， 锁定两者在 Skill 质量评测、生成方法学与运行隔离上的交集——即 AnalystBench 最值得借鉴的地方。

日期 2026-08-10 对比对象 SkillLearnBench ↔ AnalystBench 材料 本地仓库全量快照

一句话结论

二者在「Skill」一词上指向不同抽象，但在 Skill 质量评测 与 Skill 生成/迭代方法学 两个维度上高度互补。SkillLearnBench 提供轻量、可移植的 key-point coverage、teacher-feedback 多轮、 Docker 沙箱统一 runner 范式；AnalystBench 在统计门禁与版本治理上更深入。 交集即最值得借鉴之处。

01两者到底在评测什么

先对齐抽象层级，避免拿不同维度的东西硬比。

维度SkillLearnBenchAnalystBench
被测对象Skill 生成方法（one-shot / self-feedback / teacher-feedback / skill-creator）× 多模型分析报告本身，及产出报告的 Harness × Model × Skill 版本组合
Skill 的角色被评测的「产物」——方法生成的 SKILL.md 质量直接影响下游任务通过率被测的一个维度——Skill 是喂给 claude/OpenCode 的操作说明包，影响报告质量
「标准答案」形态任务有确定 verifier（pytest + reward.txt 二值）自然语言标准答案 → 编译为 Eval Spec（Claim Graph + 因果边）
评分是否确定性任务成功=是（二值 reward）；Skill/Trajectory 质量=否（GPT-5-mini judge + key-point 对齐）是（LLM 只判 match/partial/missing/contradiction，计分由确定性引擎）
任务领域20 个真实任务，跨 6 类首个官方套件 KDiag（内核/OS 分析），Core 领域无关

关键差异：SkillLearnBench 的 Skill 承载领域 know-how，AnalystBench 的 Skill 承载工具流程。二者都符合 claude SKILL.md 格式，但语义层不同——这决定了借鉴时哪些可平移、哪些需转译。

02SkillLearnBench 的核心做法

2.1 三层评测维度（最值得借鉴的整体框架）

评测明确拆成三个正交维度，每个维度有独立指标和独立实现：

维度指标度量什么实现
Task SuccessPass rate每个 trial 的二值 verifier 结果core/eval_runner.py + 任务 tests/test.sh
Skill QualityCoverage / Executability / SafetySkill 文档是否覆盖 oracle 关键点、是否可执行、是否含不安全指令evaluation/skill/metrics/compute_*.py
Trajectory QualityKey-point recall / order / completenessagent 执行轨迹是否匹配预期解决路径evaluation/trajectory/metrics/metric_*.py

对 AnalystBench 的启示：当前 Phase 1 聚焦「最终结果 Benchmark」，Phase 3 才规划 Trace。SkillLearnBench 证明三层可并行设计、独立落分，且 Skill 质量维度（coverage/executability/safety）不依赖 trace 基础设施就能先做。AnalystBench 自优化纵切目前用「报告分数 Delta」作唯一 Skill 质量代理，没有对 Skill 文档本身的质量度量——这是可借鉴的低成本增量。

2.2 Key-point Coverage：把「Skill 好不好」变成可对齐的检查项

最精巧的设计，也是和 AnalystBench 的 Claim-Graph 评分理念同源的地方。流程（compute_coverage.py）：

  1. 从 oracle（人工 skill + 成功轨迹）离线生成 skill-key-points.generated.json——该任务 Skill「应该提到」的关键知识点，每条带 reason 与 skill_reference（原文出处）；
  2. 对待评 Skill，把整个 Skill 包（SKILL.md + scripts/ + references/ + assets/）拼成一个文本 blob；
  3. 逐条 key-point 让 LLM judge 判 mentioned / missing / contradiction；
  4. coverage = mentioned / total。

与 AnalystBench 的同构：这几乎就是 Gold-Claim → Candidate-Claim 对齐，只是 SkillLearnBench 的「claim」是 Skill 文档的关键知识点，AnalystBench 的是报告的结论/证据/因果。

可直接平移：新增一个 Skill Coverage 维度——对每个被优化的 Skill，离线生成「该 Skill 应覆盖的关键操作/约束点」（从 Eval Spec 和成功轨迹抽取），候选 Skill 同样做 mentioned/missing/contradiction 对齐，作为 Gate 的硬约束或软维度。能抓住一类目前漏掉的问题——「候选 Skill 改得让报告分数涨了，但把一条必须的安全约束删了」。

2.3 四个 Skill 生成方法（连续学习方法学）

baselines/ 下四个方法，是 AnalystBench「自优化」可对标的方法学光谱：

方法信号来源轮次AnalystBench 对应
b1 one-shot无单轮Optimizer 生成候选 Patch 单次
b2 self-feedbackagent 自评轨迹K=2Evidence Builder + Mutation Generator（失败信号→patch）
b3 teacher-feedback外部 teacher LLM 给方向性建议（不露 ground-truth）K=3，失败触发 QA目前没有——只有报告分数反馈，无「领域专家方向性指导」层
b4 skill-creator无，但遵守 claude 官方 skill-creator 结构化流程单轮OptimizerPolicyVersion + 结构化 Patch

b3 teacher-feedback 最值得借鉴。AnalystBench 的 Evidence Builder 现在只从评分结果抽信号。b3 引入独立 teacher 角色，看得到 ground-truth skill，但只给「修改建议」不给答案——_B3_TEACHER_SYSTEM 明确写「Give modification suggestions only. Do NOT provide the full solution」。

对 AnalystBench 的转译：AnalystBench 的 ground-truth 是 Eval Spec（Gold Claim Graph）。可引入 EvalSpec-Aware Teacher：读得到冻结 Eval Spec，但给 Mutation Generator 的反馈只说「候选 Skill 缺少对 X 类证据的引导」「没覆盖根因判别步骤」，不直接写 Skill 内容。比纯分数反馈信息量大得多，且不泄漏标准答案到被测 agent。这是真正的方法学增量，不只是工程重构。

2.4 统一的 Docker + verifier 范式

每个任务实例结构固定：

tasks/<task>/<task>-N/
├── instruction.md        # 任务描述
├── environment/
│   ├── Dockerfile        # 沙箱环境
│   └── skills/           # oracle skill（构建时排除，防泄漏）
├── tests/
│   ├── test.sh           # verifier 入口，写 reward.txt
│   └── test_outputs.py   # pytest 断言
└── task.toml             # 元数据：难度、类别、资源、required_env

skill_runner.py / eval_runner.py 用一套流程吃所有任务：build image → run container → install agent → exec agent → exec verifier → 读 reward.txt。关键工程细节值得抄：

  • Oracle skill 防泄漏：构建上下文用 ignore_patterns("skills") 排除 oracle skill，注释明确写「prevent oracle skill leakage into no_skill or generated containers」。AnalystBench 也有「prospective holdout 不进入优化器输入」原则，但 SkillLearnBench 在构建层就物理隔离了，更稳。
  • 预构建镜像 + 运行时注入：_inject_skills_runtime 在已构建 base image 上用 docker cp 注入候选 skill，避免每次 trial 重建镜像。_parse_skill_copies 从 Dockerfile 的 COPY skills ... 指令自动推导注入路径，比硬编码路径更鲁棒。
  • token 用量抽取：_extract_token_usage 从 agent tee 日志最后一行 JSON 抽 token，按 agent 类型区分。AnalystBench 的 P19 把 token/耗时列为非目标，但这套逻辑很轻，可作 Phase 2 成本核算参考。

2.5 方法插件契约（method.py）

CONTRIBUTING.md 定义两种加方法的方式：

  • Option A（prompt-only）：放个 method.md，内容拼到 instruction 后；
  • Option B（custom orchestration）：放个 method.py，实现固定签名 run(*, container_name, task_path, trial_path, agent, model_name, instruction, task_workdir, max_rounds, max_steps) -> (passed, steps_used, stdout, stderr, rounds_used)。

b3 teacher-feedback 就是 Option B 的实现（_run_teacher_student_loop）。这个「prompt 注入 vs 插件编排」二分对 AnalystBench 的 OptimizerPolicyVersion 设计有启发：现在的 optimizer 是「prompt bundle + 结构化 patch」，等价于 Option A 增强版。未来接入更复杂的迭代方法（teacher-student、RL curator）时，需要一个 Option B 式的插件契约，而非把多轮逻辑硬塞进一个 prompt。

2.6 skills_only 模式：解耦「生成 Skill」与「用 Skill 解题」

--skills-only 让 agent 只跑「生成 SKILL.md」阶段，写完文件就中断（_poll_skills_done 轮询 + 稳定窗口），跳过 verifier。这样生成 Skill 和评估 Skill 是两次独立运行，可单独评测「方法生成的 Skill 好不好」而不混入「agent 解题能力强不强」。

对 AnalystBench 的启示：现在自优化是「改 Skill → 跑 agent 出报告 → 评报告」一体化。若想把「Optimizer 生成的 Skill 本身的质量」和「Skill 喂给 agent 后的报告质量」分开度量，这种两阶段解耦是现成范式。

03AnalystBench 已经更强的地方

借鉴不是单向的。这些地方 AnalystBench 已超出 SkillLearnBench，不要为了「对齐」而退化：

方面AnalystBenchSkillLearnBench
统计门禁Bootstrap CI + 胜率 + 灰区增采样 + 硬约束分层 + Case 级中位数无统计框架，单次 pass rate
版本治理内部 Git + 不可变 package_hash + 乐观锁 Active + provisional/validated 分级文件目录 skills/<method>-<model>/，无版本概念
数据切分诚实度明确 4-Case 用 development_regression，不宣称统计显著；prospective holdout 不进优化器20 任务 100 实例，无 train/val/test 切分意识
评分可解释性Claim Graph + 因果边 + 四级关系 + 确定性计分Skill 质量也用 LLM judge，但粒度是 key-point 二三分类
运行隔离独立 HOME + workspace + 只复制登记 Skill 包Docker 容器 + 构建时排除 oracle

保持：统计门禁是 AnalystBench 的核心壁垒；版本治理是 SkillLearnBench 完全没有的维度；小样本方法论更严谨；评分哲学更深——这些都不能为「对齐」而退。

04可行性矩阵：哪些值得做、按什么顺序

按「价值 × 实现成本」排序。成本是相对 AnalystBench 现有架构的增量。

#借鉴项价值成本优先级落点
1Skill Coverage 维度（key-point 对齐，Gate 软约束） 高中P1 skill_optimization/evidence.py 旁新增 skill_coverage.py；key-points 离线生成复用 Eval Spec 生成链路
2EvalSpec-Aware Teacher 角色（b3 转译） 高中高P1 新增 optimizer prompt evalspec_teacher.md；接入 experiment.py reflect 阶段，产「方向性建议」喂 Mutation Generator
3三层评测维度并立（Task/Skill/Trajectory 显式分离） 中高低P2 主要是文档与指标命名层；先把 Skill 质量维度从「报告分数代理」独立出来报
4method.py 插件契约（为复杂迭代方法留扩展点） 中中P2 MutationStrategy Protocol 已在附录 32 预留，补 run() 签名契约 + plugin loader
5构建层 oracle 防泄漏（物理隔离，非仅逻辑隔离） 中低P2 workspace preparer 里，对 Eval Spec / Gold Claim 物理不复制进 candidate sandbox
6skills_only 两阶段解耦（单独评测 Skill 本身） 中中P3 需先有 Skill Coverage 指标支撑，否则单独跑 Skill 无度量
7token/耗时抽取（Phase 2 成本核算） 低低P3 P19 已列为非目标，Phase 2 再说，逻辑可抄 _extract_token_usage
8Dockerfile COPY 路径自动推导 低低P3 AnalystBench 不用 Docker，仅作设计参考

两条 P1 的理由

#1 Skill Coverage：填补了自优化当前最大盲区——Gate 只看「报告分数变没变」，看不到「Skill 文档本身有没有退化掉关键约束」。SkillLearnBench 已验证 key-point 对齐可独立于任务结果工作。实现可复用 AnalystBench 已有的 Claim 对齐引擎，把「Gold Claim」换成「Skill 应覆盖的关键点」即可，工程量中等。

#2 EvalSpec-Aware Teacher：这是方法学而非工程增量。现在优化信号只有「报告哪里错了」（失败 tag），没有「Skill 应该怎么改」的方向性指导。b3 证明 teacher 看 ground-truth、只给建议、不泄漏答案的闭环可行有效。转译后，teacher 看冻结 Eval Spec（被测 agent 看不到的），产出「候选 Skill 缺什么」的结构化建议，喂给现有 Mutation Generator。能显著提升候选质量，直接提升 Gate 通过率和收敛速度。

05借鉴时的转译风险

几处不能直接照搬、需按 AnalystBench 语义转译：

  1. 「Skill」语义不同：SkillLearnBench 的 key-point 是「该知道的领域知识」。AnalystBench 的 Skill 是操作包，key-point 要重新定义为「该执行的操作步骤 / 该遵守的约束 / 该调用的接口」，不能直接套「领域知识点」。
  2. verifier 形态不同：SkillLearnBench 任务有确定 pytest verifier（二值 reward）。AnalystBench 是开放式报告，没有二值 reward——「Task Success」维度不能平移，等价物是「报告分数 + 通过阈值」，已是更细粒度度量。借鉴三层框架，不借鉴 Task Success 的实现。
  3. teacher 的 ground-truth 不同：b3 teacher 看 oracle SKILL.md。AnalystBench teacher 应看 Eval Spec（Gold Claim Graph），抽象层级不同，prompt 要重写，不能复用 _B3_TEACHER_USER 模板。
  4. 多模型矩阵：SkillLearnBench 跑 6 模型 × 4 方法做「方法×模型」研究。AnalystBench V1 明确单 Skill/单 Harness/单 Model，不需要这个矩阵，不要为「像 benchmark」而扩大被测面。

06不建议借鉴的

  • Docker 全沙箱：AnalystBench 的 workspace 隔离已够，引入 Docker 拖慢 trial、增部署依赖，得不偿失。
  • dataclaw / CTRF 日志格式：SkillLearnBench 依赖 dataclaw CLI 和 ctrf.json，是其生态产物。AnalystBench 的 run.json/result.json/artifact_json 已是稳定事实源，不要换。
  • GPT-5-mini 作为唯一 judge：SkillLearnBench 的 Skill/Trajectory 质量维度全用 GPT-5-mini judge。AnalystBench 哲学是「LLM 只判关系，确定性代码计分」，不要为对齐而退化成「LLM 直接给分」。

07建议的下一步

  1. 把本报告 #1、#2 两条 P1 拆成两个独立设计任务，分别出 spec：
    • skill-coverage-metric-design.md（Skill 质量维度设计）
    • evalspec-aware-teacher-design.md（b3 转译设计）
  2. 出 spec 前再读一遍 SkillLearnBench 的 compute_coverage.py 全文和 skill_runner.py 的 _run_teacher_student_loop——这两个函数是借鉴的最小可行参考实现。
  3. 两个 spec 都要遵守自优化设计文档（Codex v1.1）第 0 节 Codex 执行约束——复用现有 ORM/队列/Runner，不造并行 Evaluation Runner。
