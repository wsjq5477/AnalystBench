# P0 决策记录

状态：Resolved（2026-07-21）

以下决策已由项目负责人确认，作为 P1 及后续阶段的实现依据。

## D1 正向权重归一化

- A（推荐）：所有 Gold Claim + Causal Edge 权重必须合计 100，冻结时强校验。
- B：允许任意正数，运行时自动归一化到 100。

A 更直观且避免编辑结果与实际计分不同；B 编辑方便但隐藏了运行时变换。

决议：D1-A。

## D2 critical 根因冲突门禁

- A：critical root_cause 被判 contradiction 时直接判失败，同时保留诊断分。
- B：只扣额外罚分并将总分封顶 59，不直接失败。
- C（采纳）：该根因 Claim 得 0 并扣额外罚分；过程项继续计分，不直接失败且不封顶，最终只按总分阈值判断。

C 同时保留最终根因的重要性和分析过程的独立得分。

决议：D2-C。

## D3 Candidate Report 缺失的默认策略

- A（推荐）：正式 Run 默认 strict，缺任一 Case Report 拒绝启动；显式指定 partial 才允许跳过。
- B：默认 partial，缺失 Case 记 skipped 并继续。

A 适合可比 Benchmark；B 更适合探索性导入。

决议：D3-A；partial 仍可显式启用。

## D4 Candidate Claim 复用

- A：一个 Candidate Claim 可支持多个 Gold Claim，但必须逐对判断并分别留痕。
- B（采纳）：严格一对一匹配；复合句必须先拆成多个原子 Candidate Claim，不同 Claim 可以引用同一句原文。

B 防止一句宽泛描述重复得分，同时通过原子化保留紧凑报告中的多个有效结论。

决议：D4-B。

## D5 原始模型请求与响应留存

- A（推荐）：默认保存在本地 Content Store，用于审计；日志不打印，导出需显式包含。
- B：默认只保存结构化结果和请求/响应哈希，不保存完整原文。

A 可审计性强但增加敏感数据面；B 更隐私友好但难以复盘供应商异常。

决议：D5-A。

## D6 MVP 输入格式

- A（推荐）：只承诺 UTF-8 文本和 JSON；其他文件由用户预处理为文本。
- B：首版同时解析 PDF、Word 和压缩日志。

A 能集中验证评测核心；B 会显著扩大解析、安全和测试范围。

决议：D6-A。

## D7 本地任务执行

- A（推荐）：数据库持久化任务 + 独立 Local Worker，不引入 Redis。
- B：API 进程内后台任务，不提供进程中断恢复。
- C：一开始使用 Redis + 专用任务队列。

A 在本地复杂度与可靠性间较均衡。

决议：D7-A；Local Worker 必须支持数据库持久化后台任务、重启恢复和失败重试。

## D8 KDiag v0 是否进入首个 MVP

- A（推荐）：保留最小 KDiag v0，用三个离线 Case 验证 Suite 扩展机制。
- B：MVP 只做 generic-analysis，KDiag 延后。

A 可以证明 Core 与领域扩展确实解耦；B 能更快交付通用闭环。

决议：D8-A。

## D9 鉴权边界

- A（推荐）：MVP 只支持可信本机/内网单用户部署，不实现登录；文档明确不得直接暴露公网。
- B：MVP 增加单管理员 Token 鉴权。

A 范围最小；B 提供基本网络边界保护，但需要密钥生命周期和 CLI 配置。

决议：D9-A。
