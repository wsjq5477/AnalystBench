# P18 测评方式执行耗时设计

状态：Implemented（2026-07-29）

## 目标

对提交测评和定时测评中的每个 Case、每种测评方式记录实际执行时间。例如同一
Case 使用 `claude`、`script`、`skill` 三种方式时，本次正式结果能够同时展示三种
方式各自的得分与耗时。

本阶段只记录报告生成方式的执行耗时，不把排队、工作区准备和后续评分混入同一个
数字。界面统一使用“耗时”，避免把时间误称为吞吐率意义上的“速度”。

## 统一计时语义

计时对象是 `Evaluation Submission Method Run`，手工提交和定时测评继续复用同一
条 P15 执行链。

- `started_at`：子进程成功启动后立即记录的 UTC 时间。
- `finished_at`：子进程退出、超时或运行中取消时记录的 UTC 时间。
- `duration_ms`：使用单调时钟计算的实际命令执行耗时，单位毫秒。
- 排队等待、Worker 领取 Job、复制日志、构造工作区和 AnalystBench 评分耗时不计入
  `duration_ms`。
- 命令成功、非零退出、超时、输出超限和运行中取消均保留耗时。
- 在子进程启动前取消或启动失败时没有实际执行，三个字段允许为空。
- 重试开始时重置当前 Method Run 的计时字段；正式结果记录最终成功尝试，失败审计
  仍按现有 `attempt-N` 目录保留。

使用 UTC 时间用于审计，使用单调时钟计算耗时，避免系统时间调整造成负值或跳变。

## 数据与结果契约

数据库为 `evaluation_submission_method_runs` 增加可空字段：

```text
started_at    datetime UTC
finished_at   datetime UTC
duration_ms   integer
```

Case Run API 中每个 `methods[]` 项直接返回这三个字段。`run.json` 同步保存相同字段，
使运行清单不依赖数据库也能审计。

评分完成后的 `result.json` 增加独立的生成执行信息，不改变现有评分 `summary` 契约：

```json
{
  "generation": {
    "methods": [
      {
        "key": "claude",
        "version": 1,
        "status": "succeeded",
        "attempt": 1,
        "started_at": "2026-07-29T02:10:20.123Z",
        "finished_at": "2026-07-29T02:11:52.456Z",
        "duration_ms": 92333
      }
    ]
  }
}
```

`generation.methods[].key` 与评分结果中的 `candidate_name` 使用同一个测评方式 Key，
前端可以稳定合并得分和耗时。旧结果没有 `generation` 时继续正常显示，耗时展示为
`—`，不回填推算。

`result.md` 在报告排名表增加“生成耗时”列；耗时只作为运行指标，不参与得分、排名
或通过判定。

## 前端展示建议

第一层放在“测评批次”详情，当前每个 Case 下已有各方式运行状态：

```text
claude  运行中 · 已运行 38 秒
script  已完成 · 2.4 秒
skill   已完成 · 1 分 17 秒
```

- 运行状态仍沿用现有 5 秒后端轮询；取得 `started_at` 后，前端每秒使用
  `当前时间 - started_at` 重新计算“已运行”，不每秒请求后端，也不使用累加器以免
  浏览器后台标签页节流造成漂移。
- 终态显示固定 `duration_ms`。
- 未启动、启动失败或旧数据没有耗时时显示 `—`。
- 审计弹窗同时展示开始、结束和耗时，便于定位超时与失败。

第二层放在正式结果详情的“总览”表，在“得分”后增加“生成耗时”列。这里最适合直接
比较同一 Case 下 `claude / script / skill` 的质量与速度。

正式结果的“综合得分”区也在每个方案得分旁展示“生成耗时”，让用户无需下移到总览
表即可同时看到质量与时间。

## 测评批次删除

“测评批次”详情为终态批次提供删除入口：

- `completed`、`completed_with_errors`、`failed`、`cancelled` 可以确认后删除。
- 排队、生成或评分中的批次拒绝删除；用户必须先取消并等待任务停止。
- 删除范围包括 Submission、Case Run、Method Run、关联 Job、隔离工作区和该批次的
  `runs/<timestamp>/` 正式结果目录。
- 删除前把正式结果目录原子移动到隔离名称；数据库事务失败时恢复原目录，事务成功
  后再物理清理。
- 删除定时产生的批次不删除计划本身或计划触发历史；历史中的 Submission 关联变为空。

本阶段不在总览 Dashboard 增加速度图。单个 Case 的耗时容易受日志大小和机器负载
影响；后续若需要趋势分析，应按测试集和方式计算中位数、P95 与样本数，而不是只画
未经归一化的平均值。

## 兼容与边界

- 定时测评不增加专用计时字段；其创建的普通 Submission 自动获得相同能力。
- 不修改测评方式版本、命令模板、并发限制、隔离和评分契约。
- 不用 `created_at` / `updated_at` 推算耗时，因为它们包含排队、状态写入和评分阶段。
- 不把多个 Method 的耗时相加当作批次墙钟时间；并发执行时二者含义不同。
- P18 不记录评分 Judge 耗时。若后续需要，应新增独立的 `scoring_duration_ms`，不能
  与报告生成耗时复用。

## 验收条件

- 同一 Case 使用三种测评方式后，API、`run.json`、`result.json` 和 `result.md` 均
  能识别三种方式各自的耗时。
- 手工提交和定时测评返回完全一致的计时结构。
- 成功、非零退出、超时和运行中取消均保留非负耗时。
- 排队等待不进入 `duration_ms`，并发 Method 的计时互不覆盖。
- 重试后的正式结果绑定最终成功尝试；旧结果继续可读。
- 前端批次详情和正式结果总览在深浅主题下均正确展示秒、分秒和空值。
- 终态批次可以删除运行记录和正式结果；运行中批次返回稳定的 409 错误。
- 数据库迁移、后端测试、前端单元测试、生产构建和 Sites Worker 测试通过。

## 已确认决策

- P18 的正式“耗时”只计算子进程实际执行，不包含排队、工作区准备和评分。
- 正式结果综合得分区和总览增加“生成耗时”，批次详情每秒显示运行中计时并在终态
  显示固定耗时。
- Dashboard 暂不增加速度趋势；需要趋势时另行设计中位数/P95 聚合。
- 重试后的正式结果只展示最终成功尝试耗时，历史失败尝试继续通过审计目录查看。
- 测评批次详情支持安全删除终态批次及其正式结果，运行中必须先取消。
